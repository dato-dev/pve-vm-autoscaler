# CLAUDE.md

Инструкции для Claude Code при работе в репозитории `pve-vm-autoscaler`.

`pve-vm-autoscaler` — автоскейлер VM для Proxmox VE. Агент внутри VM шлёт CPU/RAM/disk метрики на сервер,
сервер хранит временные ряды в TimescaleDB и клонирует новую VM из template через Proxmox API,
когда средняя нагрузка в окне превышает пороги policy.

Цели и план развития: [ROADMAP.md](ROADMAP.md). Инструкции по запуску: [README.md](README.md).

## 1. Обязательные правила

Эти правила действуют для **любого** изменения кода в репозитории.

### 1.1 Комментировать код

- **JSDoc на каждой экспортируемой функции, классе и методе.** Обязательно: назначение,
  `@param` для неочевидных аргументов, `@returns`, `@throws` если функция кидает.
- **Комментарий `//` там, где код объясняет "как", но не "почему".** Комментируй:
  - магические числа и единицы измерения (`df -kP` отдаёт килобайты → `* 1024`);
  - обходные пути и особенности Proxmox API
    (например: `full=0` означает linked clone — семантика инвертирована относительно имени поля);
  - решения, принятые ради корректности (порядок проверок в `evaluateScalingDecision` значим:
    cooldown проверяется раньше порогов);
  - всё, что читатель через полгода спросит «почему так?».
- **Не комментируй очевидное.** `// увеличиваем счётчик` над `i++` — мусор.
- **Язык комментариев — русский**, как и вся документация проекта.
  Имена сущностей в коде — английские.
- Комментарий, который врёт, хуже отсутствующего: правишь код — правь комментарий.

### 1.2 Тест на каждую новую функцию

- **Новая экспортируемая функция или метод не мёржится без теста.** Это жёсткое правило.
- Тест-файл лежит рядом с исходником: `decision.ts` → `decision.test.ts`.
- Фреймворк — **vitest** (`npm test` = `vitest run`).
- Минимум для каждой функции: happy path + граничный случай + путь с ошибкой.
- Для чистых функций (`evaluateScalingDecision`, `labelsMatch`, `parseLabels`) — прямые unit-тесты
  без моков; они самые дешёвые и самые ценные.
- Для кода с побочными эффектами — тестируй через интерфейс:
  `ScaleProvisioner` подменяется фейком, БД — testcontainers или pg-mem, HTTP — `app.inject()` у Fastify.
- **Правишь баг — сначала пиши падающий тест**, потом чини.
- Меняешь сигнатуру — обнови существующие тесты, не удаляй проверки ради зелёного прогона.

### 1.3 Обновлять ROADMAP.md

- Реализовал пункт milestone — отметь `[x]` и, если ограничение из раздела 3 закрыто, убери его.
- Обнаружил новое ограничение — добавь строку `L#` в раздел «Известные ограничения».
- Появилась новая идея вне текущего плана — добавь в «Backlog», не раздувай активный milestone.
- Обнови «Последнее обновление» датой изменения.

### 1.4 Обновлять README.md

README — документ для пользователя, не для разработчика. Обновляй его, если изменение затронуло:

- переменные окружения (`.env.example`, `infra/agent.env.example` — синхронно);
- поля scaling policy (обнови `infra/policy.example.json` и раздел «Конфигурация policy»);
- HTTP-эндпоинты и их контракты;
- шаги запуска, деплоя или установки агента;
- архитектуру — тогда обнови и mermaid-диаграммы.

**Все схемы — mermaid прямо в markdown**, не картинки. Диаграмма должна быть видна в диффе
и правиться текстом; бинарные `.svg`/`.png` в репозиторий не кладём (`*.svg` в `.gitignore`).

Секретов в README быть не должно — только плейсхолдеры вида `change-me` и `example.com`.

### 1.5 Коммиты: Conventional Commits + semantic-release

Версия и CHANGELOG генерируются **из текста коммитов**. Небрежное сообщение — это не косметика,
а неправильно выпущенный релиз, поэтому формат обязателен.

**Формат:**

```
<тип>(<компонент>): что сделано

Что именно изменилось и почему. Описание — по существу, не пересказ диффа.

BREAKING CHANGE: <что сломалось и как мигрировать>   ← только если ломающее
```

Заголовок — в повелительном наклонении, без точки в конце, до ~72 символов.

**Типы и их влияние на версию:**

| Тип | Назначение | Версия |
|---|---|---|
| `feat` | новая функциональность | minor |
| `fix` | исправление бага | patch |
| `perf` | оптимизация без смены поведения | patch |
| `refactor` | изменение кода без смены поведения | нет релиза |
| `test` | тесты | нет релиза |
| `docs` | документация, включая ROADMAP.md и README.md | нет релиза |
| `ci` | пайплайны, workflow | нет релиза |
| `build` | сборка, Dockerfile, зависимости | нет релиза |
| `chore` | всё остальное | нет релиза |
| любой с `!` или футером `BREAKING CHANGE:` | ломающее изменение | major |

> **Пока версия ниже 1.0.0** semantic-release поднимает ломающее изменение до **minor**, а не major:
> `0.2.0` → `0.3.0`. Это ожидаемо и совпадает с версиями milestone'ов в [ROADMAP.md](ROADMAP.md).
> Футер `BREAKING CHANGE:` всё равно обязателен — он попадает в CHANGELOG.

**Компоненты (scope):** `agent`, `agent-go`, `server`, `evaluator`, `metrics`, `db`, `policy`,
`proxmox`, `shared`, `infra`, `release`. Выбирай по тому, что изменилось с точки зрения пользователя;
если сомневаешься — имя пакета.

**Одна фича — один коммит.** Практически это значит:

- Тесты (п. 1.2), комментарии (п. 1.1) и правки ROADMAP.md / README.md (пп. 1.3, 1.4)
  входят **в тот же коммит**, что и сама фича. Отдельный коммит «добавил тесты к вчерашнему» — ошибка.
- Не смешивай рефакторинг с функциональным изменением: сначала `refactor`, отдельным коммитом,
  потом `feat`. Иначе в диффе не видно, что именно изменило поведение.
- Не дроби одну фичу на «часть 1 / часть 2». Если она не влезает в один коммит — это не одна фича,
  и её надо разделить по смыслу, а не по объёму.
- Правки по итогам ревью — `amend` в исходный коммит, а не `fix: правки после ревью`.

**Примеры из текущего плана:**

```
fix(agent): считать память по MemAvailable вместо MemFree

os.freemem() на Linux возвращает MemFree, поэтому page cache и reclaimable-память
попадали в «использовано». На прогретой машине memoryPercent завышался на десятки
процентов и вызывал ложные scale-up при пороге 80%.

Читаем MemAvailable из /proc/meminfo, с fallback на os.freemem() для не-Linux.
```

```
feat(policy)!: перевести конфигурацию на YAML

Загрузчик читает .yaml/.yml через парсер `yaml` (YAML 1.2 — в 1.1 значения
no/off/yes/on стали бы булевыми и ломали произвольные метки в selector).
nodeTemplates отделены от policies, длительности и объёмы записываются
строками (5m, 2Gi, 60%).

BREAKING CHANGE: infra/policy.example.json заменён на policy.example.yaml,
поля переименованы (targetNode → hypervisor, minNodes/maxNodes → nodes.min/max).
Конвертация старых файлов: `pve-vm-autoscaler migrate-policy <file>`.
```

```
ci(release): подключить semantic-release и commitlint
```

```
docs(roadmap): отметить M1.8 выполненным
```

**Пока проект не под git** (M1.7) правило действует с момента `git init`;
настройка semantic-release и commitlint входит в тот же пункт.

## 2. Структура проекта

```
apps/
  agent/src/
    index.ts       — цикл сбора и отправки, backoff при сбоях
    config.ts      — загрузка AGENT_* env, парсинг labels
    metrics.ts     — сбор CPU/RAM/disk
    client.ts      — POST /v1/metrics с Bearer-токеном
  server/src/
    index.ts       — composition root: config → миграции → app → evaluator
    app.ts         — сборка Fastify, регистрация роутов
    config/env.ts  — ServerConfig, загрузка и валидация policy-файла
    routes/        — HTTP-эндпоинты
    security/      — аутентификация агентов
    db/            — pool, migrate (SQL инлайном), repository (весь SQL)
    evaluator/
      decision.ts  — ЧИСТАЯ функция решения (главная бизнес-логика)
      worker.ts    — таймерный цикл, оркестрация решения и provisioning
      types.ts     — интерфейсы ScaleProvisioner, StructuredLogger
      proxmoxProvisioner.ts — реализация ScaleProvisioner
packages/
  shared/src/index.ts   — Zod-схемы контрактов + выведённые типы
  proxmox/src/index.ts  — HTTP-клиент Proxmox API
infra/                  — policy.example.json, agent.env.example
scripts/                — install-agent-rhel.sh (systemd-юнит агента)
```

**npm workspaces + TypeScript project references.** Зависимости между пакетами идут по алиасам
`@pve-vm-autoscaler/shared` и `@pve-vm-autoscaler/proxmox`, а не по относительным путям.
Добавил новый пакет — впиши его в `tsconfig.build.json` → `references`.

## 3. Архитектурные инварианты

Нарушать их нельзя без явного согласования с пользователем.

1. **`evaluateScalingDecision` остаётся чистой функцией.** Никакого I/O, никакого `new Date()`
   без параметра `evaluatedAt` (иначе тесты станут недетерминированными).
   Вся работа с БД и Proxmox — в `worker.ts` и провижнере.
2. **Контракты живут только в `packages/shared`.** Новое поле в метриках или policy — сначала
   Zod-схема там, тип выводится через `z.infer`. Не дублируй интерфейсы вручную.
   **Это правило распространяется и на Go-агента** (M6): его структуры генерируются из той же
   Zod-схемы через JSON Schema. Написанная руками Go-структура, повторяющая контракт, —
   ошибка, а не оптимизация.
3. **Весь SQL — в `db/repository.ts`.** Роуты и evaluator не знают о Postgres.
4. **Provisioning — за интерфейсом `ScaleProvisioner`.** Это точка, где тесты подменяют Proxmox.
   Аналогично метрики — за `MetricsSource` (M4): evaluator не знает, откуда пришли числа,
   из TimescaleDB или из PromQL.
5. **Dry-run — безопасный дефолт.** `loadServerConfig` включает dry-run на всё, кроме явного
   `PROXMOX_DRY_RUN=false`. Не инвертируй эту логику.
6. **`packages/proxmox` не зависит от Fastify/pg** — это переиспользуемый клиент;
   логгер приходит через интерфейс `ProxmoxLogger`.
7. **Каждая операция с Proxmox — асинхронный task**, который нужно дождаться через `waitForTask`.
   Не считай операцию выполненной по факту HTTP-ответа.
8. **Policy — интерфейс оператора, а не структура данных.** Добавляя поле: единица измерения
   явная (`5m`, `2Gi`, `60%`, а не `*Seconds`/`*Mb`), место выбирается по частоте изменения
   (тюнинг → `policies`, свойства машины → `nodeTemplates`), ошибка валидации указывает на поле.
   **Поле, которое код не читает, — баг**, а не задел на будущее (см. `sampleIntervalSeconds`, L22).

## 4. Стиль кода

- TypeScript ESM (`"type": "module"`), **импорты с расширением `.js`** — требование NodeNext.
- `strict: true` + `noUncheckedIndexedAccess: true`. Индексный доступ даёт `T | undefined` —
  проверяй, не подавляй через `!`.
- `any` запрещён. Внешние данные приходят как `unknown` и валидируются Zod-схемой.
- Функции возвращают явные типы. Ошибки — `throw new Error` с контекстом в сообщении.
- Именование: `camelCase` в TS, `snake_case` в SQL, маппинг — в репозитории.
- Логи структурные, первым аргументом объект с полем `event` в точечной нотации:
  `proxmox.vm.clone.started`, `scaling.decision`, `metrics.ingested`.
  Длительности — в полях `durationMs`.
- **В логи не попадают секреты**: токены, `PROXMOX_TOKEN_SECRET`, содержимое заголовка `authorization`.

## 6. Безопасность

- **Никогда не коммить реальные секреты.** В `docker-compose.yml` сейчас лежит настоящий
  Proxmox-токен (`M1.1` в ROADMAP) — при первой же правке этого файла вынеси его в env и скажи
  пользователю, что токен нужно ротировать.
- `.env` в `.gitignore`; примеры содержат только `change-me` и `example.com`.
- `PROXMOX_TLS_REJECT_UNAUTHORIZED=false` допустим только для локальной лаборатории —
  в примерах и документации оставляй `true`.
- Токен агента сравнивай constant-time; не логируй его даже частично.
- Не расширяй права Proxmox-токена «на всякий случай»: нужны только clone/config/start
  (и shutdown/delete после Milestone 4).

## 7. Как добавлять функциональность

Порядок шагов при типичной задаче:

1. Прочитай соответствующий пункт milestone в ROADMAP.md — возможно, задача уже описана.
2. Если задача меняет контракт — начни со схемы в `packages/shared`.
3. Реализуй логику; чистую часть выдели в отдельную функцию, чтобы её можно было тестировать.
4. Напиши тесты (п. 1.2) — happy path, граница, ошибка.
5. Прокомментируй неочевидные решения (п. 1.1).
6. Обнови ROADMAP.md (п. 1.3) и README.md (п. 1.4), если изменение их касается.
7. Прогони build / test / lint.
8. Оформи **один** коммит по Conventional Commits (п. 1.5) — код, тесты и документация вместе.
   Ломающее изменение обязано нести футер `BREAKING CHANGE:`.

**Не делай сверх запрошенного.** Заметил проблему за рамками задачи — опиши её в
«Известных ограничениях» ROADMAP.md и скажи пользователю, но не чини молча в том же изменении.

## 8. Важный контекст

- Проект **не под git** (`git init` ещё не выполнен) — пункт `M1.7` в ROADMAP.
- В корне лежит `Безымянный-2026-05-10-1135.svg` — черновая схема архитектуры, к сборке отношения не имеет.
- Главный функциональный пробел MVP — **отсутствие scale-down** (Milestone 4): пул только растёт.
- Известный race: VM в процессе provisioning не учитывается в `maxNodes` — описан в README
  («Целевая схема») и в Milestone 3.
- **Формат политик меняется на YAML со сменой структуры** (Milestone 2): `nodeTemplates` отдельно
  от `policies`, duration/quantity/percent-строки (`5m`, `2Gi`, `60%`), переименования полей.
  Это ломающее изменение, и оно намеренно поставлено рано — пока политик в проде нет.
  **Не добавляй новые поля в текущую JSON-схему политики**, если M2 ещё не сделан:
  их придётся мигрировать дважды. Парсер YAML — `yaml` (1.2), не `js-yaml` (1.1 превращает
  `no`/`off`/`yes`/`on` в булевы, а в `selector` лежат произвольные пользовательские метки).
- **Агент переезжает на Go** (Milestone 7). `apps/agent` на Node становится legacy;
  новую функциональность агента добавляй с оглядкой на то, что её придётся переносить.
- **Источник метрик становится подключаемым** (Milestone 5): TimescaleDB или Prometheus/VictoriaMetrics.
  Не завязывай новую логику evaluator напрямую на SQL — только через `MetricsSource`.
- В ROADMAP есть раздел **«Открытые архитектурные решения» (ADR)**. ADR-1 (Proxmox как источник
  истины об инвентаре) и ADR-2 (`desiredNodes` вместо булева решения) **не приняты**.
  Не реализовывай их без явного согласования — но и не строй поверх решений, которые они отменят.
